# 设计

本文只记录**从代码里看不出来、但决定了代码形状**的判断。用法看 README，
排版政策、默认值出处与中文正文的推荐开关组看 [`text-rules.md`](text-rules.md)。

## 边界为什么切在这里

引擎的输入是**已解析、已级联**的 `Document`，输出是**已完成布局**的显示列表。

- 解析（EPUB/XHTML/CSS）留在宿主：那部分永远是变化最快的，绑进核心会让核心
  被迫跟随 CSS 规范的版本走。
- 光栅化留在宿主：GPU / 软件 / e-ink 的选择是产品决策，不是排版决策。
  **画质责任也随像素一起归下游**：hinting、gamma、亚像素 AA 的取舍是这条边界的
  一部分，不是核心的遗漏。
- CFI 留在宿主：它是 EPUB 的坐标系统，不是排版的坐标系统；核心只提供
  `Location`，由宿主映射。

代价是宿主必须自己完成编译那一半。这是有意的：本库服务的是"已经有编译器的宿主"，
而不是"想直接打开一个 epub 文件的人"。

## 不变量

这些在实现里是结构，不是约定；改动它们都会同时改动测试：

1. **分页与滚动共享同一份断行与块布局**，只有"取窗口"不同。位置、锚点、字号
   变化不会因为模式切换而分裂。
2. **布局预计算，绘制惰性**。`Layout` 建好时只存行盒、块盒、页映射、锚点，以及每个
   item 的 y 与所属 unit；`flowItem` 是按需物化的视图，不是存储。DisplayList 在首次
   访问 `Page`/`Tile` 时生成并缓存。
3. **不存全书 shaped glyph，也不存原文副本**。行盒只记 rune 区间和度量，绘制时按行
   重新 shaping（经有界行缓存）。500 万字全书 shaped glyph 约 450 MB，不可接受。
   同理：段落不保留 `[]rune` 拷贝（`paraSeg` 只记源字符串，worker 缓冲按需物化），
   flow 不为每行物化 `flowItem`（只存 y 与 unit 下标，其余由 cache 的断行结果推导）。
4. **两遍式**：断行 → 分页。改行高、段间距、页高不需要重新 shaping 或断行。
5. **缓存 key 是输入哈希，不是失效传播**。任何改变断行/分页结果的输入必须进
   `BreakKey`/`PageKey`；新增政策字段靠整体哈希结构体自动进 key。
6. **无全局状态**：没有 `init()`、没有注册表、没有日志。并行的 helper goroutine 属于
   一次 phase（`Engine.parallelFor`），phase 返回前 join；唯一会跨调用存活的是
   `StartPrefetch` 显式返回的句柄，宿主持有它并 `Wait`/取消。库不替宿主决定何时后台做事。
7. **确定性**：不同 `Workers` 数量产出逐字相同的布局；测试直接比对两条路径。
8. **文档、字体集合、`Layout` 构建后不可变**，可并发读；唯一可变的是内部缓存。

## 为什么分段不走 bidi

`shaping.Segmenter.Split` 对每段都跑 UAX #9，即使这个引擎只产出 LTR。go-text 的短路
条件很保守：只要有一个 rune 的 bidi 类是 `{L, EN, ES, CS, WS}` 之外的（CJK 标点是 ON），
整段就跑完整算法——实测 160 字中文段落 6.3 KB 分配，把标点换成汉字后是 0。

所以 `render/segment.go` 自己做 script + face 切分：规则照抄 go-text v0.3.5
（`splitByScript`、`splitByFace`、`enforceLanguages` 与成对标点表，附出处），只在
"全部是简单脚本（Latin/CJK/Hangul/Greek/Cyrillic + Common）且无双向控制符"时走快路径，
其余一律回落到 `Segmenter.Split`——复杂脚本（Arabic/Indic/Thai…）与 RTL 的正确性不受
影响，代价是那条路径仍然分配。切分结果由 `scripts/linecmp.sh` 的四组语料逐行比对钉死。

## 并发怎么切

三个边界决定了现在的形状。

**段落是断行的最小单位。** shaping 与断行只依赖段落自己的文本、样式和宽度，所以段落
之间天然独立。断行因此分三段（`planChapter` → `breakParagraphs` → `attachLines`）：
规划只做样式继承、inline 分词和建块树（O(nodes)，不 shaping），然后把**全书**段落汇成
一个扁平任务列表让 worker 抢，最后顺序把行盒贴回块树。只按顶层块并行是不够的：一整章
正文包在一个 `<div>` 里的书写法很常见，那样并行度会退化成 1。

**分页按章独立。** 每章从自己的顶端开始贪心分页，页号只是拼装时累加，所以
stack+paginate 可以按章并行；页内的贪心扫描本身仍按行串行（页的起点依赖上一页的
结束，拆开就要做前缀和，收益不抵复杂度）。改行高/段间距的重排只剩这一段，所以它
是交互延迟的大头。

**显示的并行单位是行。** 一页/一个 tile 是几十行，每行独立 shaping、独立产出 ops，
建完再按文档序拼回 `Page`/`Tile`。行缓存因此分片（16 片），否则并行建页会挤在同一把
锁上。

**并发预算是 Engine 级、不阻塞的。** `Options.Workers` 是整个 Engine 的上限而不是每次
调用的上限：活跃 phase 数决定每个 phase 能拿到的份额，helper 抢不到预算就不起
goroutine、由调用方自己跑完，所以没有等待、没有死锁；helper 发现自己超出份额时会在
下一个任务边界退出并交还预算。这样并发布局、预取、前台重排共用一个机器，而不是各自
起一套 worker 互相踩。按页并行、而不是按块并行，是把大任务切成小任务的直接结果：
4 µs 的段落任务比 100 µs 的块任务更容易被均衡分配，但也要小心任务太碎的调度开销
（helper 的份额检查因此每 8 个任务做一次）。

## 明确不做

| 不做 | 理由 |
|---|---|
| EPUB/OPF/XHTML/CSS 解析 | 见"边界"；解析器应作为独立 module |
| 光栅器、字体加载、图片解码 | 宿主的事；核心只传 `ImageID` 与字体字节 |
| fixed-layout、脚本化内容 | 不可重排，与"分页是纯函数"的前提冲突 |
| 内置字体、断词词典、预设 | 体积与审美都不该由核心决定；核心只给 `Hyphenator` 接口，词典是独立包（`render/hyphen/en`），核心不 import |
| 可变文档树 / 增量失效传播 | 内容哈希缓存已经覆盖了实际的重排场景，且不需要标记正确性 |
| 隐藏的后台 goroutine | 生命周期必须由宿主掌握；要后台预取就显式拿 `StartPrefetch` 的句柄 |

## 会破坏当前结构的能力

目前 IR 是扁平 arena，节点只有 block/inline/text/image/br。以下能力需要"祖先的
尺寸约束子节点的排布"，扁平结构表达不了，实现时必须先扩 IR（而不是硬塞）：

- 表格：行列组、跨行列，本质是网格 + 约束求解。
- flex / grid：尺寸在多级之间协商。
- ruby / 竖排：行内需要第二套沿行轴的排布与断行规则。

标题不孤行（`keep-with-next`）、脚注、浮动环绕不需要新模型：它们可以在现有的
块/行结构和分页器上追加，但各自的规则仍需单独设计。
