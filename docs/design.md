# 设计

本文只记录**从代码里看不出来、但决定了代码形状**的判断。用法看 README，
排版政策看 [`text-rules.md`](text-rules.md)，与其他引擎的对照看
[`prior-art.md`](prior-art.md)。

## 边界为什么切在这里

引擎的输入是**已解析、已级联**的 `Document`，输出是**已完成布局**的显示列表。

- 解析（EPUB/XHTML/CSS）留在宿主：那部分永远是变化最快的，绑进核心会让核心
  被迫跟随 CSS 规范的版本走。
- 光栅化留在宿主：GPU / 软件 / e-ink 的选择是产品决策，不是排版决策。
  **画质责任也随像素一起归下游**：hinting、gamma、亚像素 AA 的取舍是这条边界的
  一部分，不是核心的遗漏。
- CFI 留在宿主：它是 EPUB 的坐标系统，不是排版的坐标系统；核心只提供
  `Location`，由宿主映射。

代价是宿主必须自己完成编译那一半。这是有意的：本库服务的是"已经有编译器的宿主"，
而不是"想直接打开一个 epub 文件的人"。

## 不变量

这些在实现里是结构，不是约定；改动它们都会同时改动测试：

1. **分页与滚动共享同一份断行与块布局**，只有"取窗口"不同。位置、锚点、字号
   变化不会因为模式切换而分裂。
2. **布局预计算，绘制惰性**。`Layout` 建好时只存行盒、块盒、页映射和锚点；
   DisplayList 在首次访问 `Page`/`Tile` 时生成并缓存。
3. **不存全书 shaped glyph**。行盒只记 rune 区间和度量，绘制时按行重新 shaping
   （经有界行缓存）。500 万字全书 shaped glyph 约 450 MB，不可接受。
4. **两遍式**：断行 → 分页。改行高、段间距、页高不需要重新 shaping 或断行。
5. **缓存 key 是输入哈希，不是失效传播**。任何改变断行/分页结果的输入必须进
   `BreakKey`/`PageKey`；新增政策字段靠整体哈希结构体自动进 key。
6. **无全局状态**：没有 `init()`、没有注册表、没有日志、没有隐藏 goroutine。
   需要异步或后台重排，由调用方显式控制。
7. **确定性**：不同 `Workers` 数量产出逐字相同的布局；测试直接比对两条路径。
8. **文档、字体集合、`Layout` 构建后不可变**，可并发读；唯一可变的是内部缓存。

## 为什么按章/段落并行

shaping 与断行对每个段落独立，这条边界天然存在；分页依赖前一页的结果，是串行的。
所以并行粒度停在"块"，合并页号在单线程里 O(pages) 完成。反过来，按页并行需要
先知道每页起点，等于把串行部分提前，收益为负。

## 明确不做

| 不做 | 理由 |
|---|---|
| EPUB/OPF/XHTML/CSS 解析 | 见"边界"；解析器应作为独立 module |
| 光栅器、字体加载、图片解码 | 宿主的事；核心只传 `ImageID` 与字体字节 |
| fixed-layout、脚本化内容 | 不可重排，与"分页是纯函数"的前提冲突 |
| 内置字体、断词词典、预设 | 体积与审美都不该由核心决定；断字只给接口 |
| 可变文档树 / 增量失效传播 | 内容哈希缓存已经覆盖了实际的重排场景，且不需要标记正确性 |
| 隐藏的后台 goroutine | 生命周期必须由宿主掌握 |

## 会破坏当前结构的能力

目前 IR 是扁平 arena，节点只有 block/inline/text/image/br。以下能力需要"祖先的
尺寸约束子节点的排布"，扁平结构表达不了，实现时必须先扩 IR（而不是硬塞）：

- 表格：行列组、跨行列，本质是网格 + 约束求解。
- flex / grid：尺寸在多级之间协商。
- ruby / 竖排：行内需要第二套沿行轴的排布与断行规则。

标题不孤行（`keep-with-next`）、脚注、浮动环绕不需要新模型：它们可以在现有的
块/行结构和分页器上追加，但各自的规则仍需单独设计。
