# 业内参考笔记：排版与文档模型

> 一份**参考**，不是规范，也不是决策记录。
> 目的是把"别人怎么想的"摆在一起，方便以后需要时对照，而不是要求本项目照做。
> 内容凭记忆整理，细节（尤其是版本与年份）可能有出入，引用前请复核原文。

## 为什么值得看别人的设计

Brooks 的区分在这里很好用：

- **本质复杂度**：问题本身固有的，比如断行、双向文本、级联、增量失效。
- **偶然复杂度**：某个时代、某个约束带来的代价，比如为兼容旧 API 而保留的结构。

浏览器三十年的积累里，两者混在一起。照抄全部会背上偶然复杂度，全部否掉会重犯本质复杂度。
判断标准大概是：**这个结构是为了"可变 + 任意页面 + 增量失效"，还是为了"不可变 + 长文档 + 批处理"？**

## 各家的核心模型

| 系统 | 核心数据结构 | 值得看的地方 | 不值得看的地方 |
|---|---|---|---|
| **TeX**（1978） | 盒子 + glue + penalty 的扁平水平/垂直列表 | 断行与分页是两遍；分页作用在垂直列表上；最优断行（Knuth–Plass） | 宏语言、全局状态、单线程 |
| **PDF** | 页面 = 扁平内容流 + 资源字典 | 显示列表作为"已完成布局"的序列化边界 | 不可回流，无文档结构 |
| **Typst**（2023） | content tree → layout → `Frame`（扁平显示列表）；`comemo` 按输入哈希做记忆化 | 布局是纯函数；增量靠输入哈希，不靠可变失效传播 | 脚本语言、树遍历解释器的开销 |
| **LayoutNG**（Chrome 2019+） | 不可变 fragment tree，与 DOM 分离 | 布局产物与文档树解耦；fragment 可序列化 | fragment 树本身仍很重 |
| **Servo** | Rayon 并行布局，按 fragment 分片 | 并行粒度的经验：哪些阶段可并行、哪些注定串行 | 过度并行带来的调度与同步成本 |
| **Android PrecomputedText** | 后台预计算文本布局，主线程复用 | "测量一次、复用"的工程化做法 | 只管文本，不管分页 |
| **Flutter RenderObject** | 可变渲染树 + relayout boundary / repaint boundary | **"边界"**概念：哪部分缓存不依赖祖先变化 | 可变树 + 全量标记失效 |
| **WeasyPrint / Prince** | 自建 box 树，两遍式分页 | 与 TeX 一致的两遍结构 | 完整 CSS 引擎的体量 |
| **Paged.js / Vivliostyle** | 在浏览器之上测量 DOM，克隆 fragment 做 paged media | 说明分页需求真实存在且浏览器不提供 | 靠测量 DOM 反推分页，根本性脆弱 |
| **KOReader / crengine** | 自有 box 模型，针对 e-ink 优化 | e-ink 的刷新/脏区约束如何影响架构 | 历史包袱重，C++ |

## 浏览器被反复讨论的三处设计

这些更像是**架构耦合**的问题，而不是"年代久远"：

1. **文档树同时是布局的唯一真相。**
   没有独立、不可变的布局产物，于是"某一处变了"必须沿可变树传播。
   LayoutNG 花了很久才把 fragment tree 与 DOM 分开，这件事本身就是一个论据。

2. **样式计算与布局应用没有硬边界。**
   样式重算和布局重算会互相触发，外部很难推理"这次改动影响了什么"。

3. **布局、绘制、合成共用一棵树。**
   缺少清晰的显示列表边界，于是"滚动掉帧"和"重排"在实现上纠缠，代价无法分档。

共同点：**没有把"不可变的数据"当作模块之间的边界。**
这一条值得记住，但不必上升为教条——单页、交互密集的编辑器这类场景，可变模型反而更合适。

## 可以直接参考的几个思路

| 思路 | 出处 | 大致含义 |
|---|---|---|
| 两遍式（断行 → 分页） | TeX、WeasyPrint | 断行结果与页面切分是两个层次，改页高不该重断行 |
| 布局 = 纯函数 + 记忆化 | Typst `comemo` | 以输入哈希为 key 缓存阶段产物，而不是靠失效传播 |
| 不可变的布局产物 | LayoutNG fragment | 布局结果可序列化、可跨线程传递、可断言不变 |
| 重排/重绘边界 | Flutter | 明确"哪一层缓存会因为什么失效" |
| 结构化扁平数组 | 数据导向设计（Acton） | 前序排列 + 深度，子树即连续区间；顺序扫描、无指针追逐 |
| 显示列表作为输出边界 | PDF、Typst `Frame` | 引擎的输出是数据，不是"能画的东西" |

## 树在哪里是本质的

"尽量扁平"不等于"永远扁平"。以下场景中，祖先信息参与子节点排布，嵌套结构难以回避：

- **表格**：行组/列组/跨行列，本质是网格 + 约束求解。
- **flex / grid**：尺寸约束在多级之间协商。
- **最优断行**：需要跨行的代价回填（可以用前缀和表达，但算法本身是全局的）。
- **双向文本**：游标、镜像、run 重排——不过这是行内 run 级别，不是文档树级别。

一个粗略的判据：**如果需要"祖先的尺寸约束子节点的排布"，嵌套是本质的；
如果只是"分组、归属、顺序"，扁平 + 区间通常够。**

## 与本项目的对照（仅供参照）

| 概念 | 本项目现状 | 上面这些系统的对应物 |
|---|---|---|
| 输入文档 | `Document`：章 → `[]Node`（目前带 `Children`） | DOM / content tree / box tree |
| 样式 | `Style` 固定字段 + `StyleID` 去重值表 | CSSOM / computed style |
| 断行 | `shapedRun` + `flowItem` 平铺 | box list / inline fragment |
| 分页 | `pageInfo`（章 + item 区间） | TeX 垂直列表分页 / paged media |
| 输出 | `drawOp` 扁平数组 | 显示列表 / `Frame` / content stream |
| 位置 | `Location`（章、节点、rune 偏移） | CFI / 锚点 / 文本偏移 |
